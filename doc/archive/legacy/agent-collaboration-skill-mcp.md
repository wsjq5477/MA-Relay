# 方案 2：通过 Skill / MCP 实现多设备 Agent 发现与协作

日期：2026-10-10  
状态：产品设计备忘，供后续需求评审与开发使用；本文描述的方案尚未交付。

2026-10-10 用户最新要求：发现身份改为机器上的工具节点，不绑定项目/模型/供应商；用户指定主节点和允许连接的子节点。最新调整与分增量验收见 [I05 提案](../../iterations/I05/proposal.md)。本文下方关于项目实例身份及由发起者临时担任协调者的建议保留为历史备选，不作为新需求基线。

## 1. 产品定位

让用户正在使用的 Agent，能够发现并联系其他设备上的 Agent，交换信息、委派任务、接收结果，并继续当前工作。

用户可以继续使用原来的 Agent 入口。AgentBridge 提供跨设备连接、身份与能力发现、消息投递、任务状态和结果管理；Skill / MCP 将这些能力接入 Agent。

多设备的价值来自不同环境拥有的代码、数据、工具、账号权限、算力或持续运行能力。不同设备上的 Agent 不必使用相同工具或模型。

## 2. 与方案 1 的关系

方案 1 侧重在产品中组织协作：用户选择主 Agent，由它分配任务并汇总结果。

方案 2 侧重让已有 Agent 获得协作能力：Agent 在用户授权范围内发现其他 Agent，联系对方并请求帮助。

两种方案可以共享同一套通信和任务基础设施。初版建议由任务发起 Agent 担任本次任务的协调者，不要求永久指定全局主 Agent。后续管理界面可以增加参与者选择、角色配置、任务看板与人工接管。

通信经过 Hub，并不意味着 Hub 是主 Agent。Hub 管理连接与执行状态；任务拆分、协作选择和结果判断由协调 Agent 完成。

## 4. Skill、MCP 与设备接入端的分工

| 组成 | 职责 |
| --- | --- |
| Skill | 告诉 Agent 何时联系其他 Agent、怎样描述请求、传递哪些上下文、如何处理补充问题和检查结果 |
| MCP Server | 暴露查询 Agent、发消息、委派任务、观察状态、读取结果和请求取消等操作 |
| AgentBridge 核心 | 管理可信身份、可见范围、注册、路由、消息与任务记录、状态关联和恢复 |
| 设备接入端 | 在对应设备上登记工具 / 实例、保持连接、接收请求并回传消息与结果 |
| 工具适配器 | 根据目标工具实际接口，创建任务、继续托管会话、读取回复或处理控制请求 |
| 管理界面 | 让用户查看设备、参与者、消息、任务、等待事项与交付物，并控制协作 |

Skill 是协作指导，需要可调用的 MCP 或 CLI 等操作能力。MCP 是接入接口，实际跨设备投递和执行仍由 AgentBridge、设备接入端及适配器完成。

目标 Agent 配置了 MCP，不等于它就能被远程唤醒或向当前聊天窗口注入消息。每种适配器必须明确其支持的接收方式。

## 5. 核心对象与发现信息

沿用现有机器、工具连接、项目实例、会话和任务的层次。Agent 可协作身份应能定位到对应设备与执行实例；一次交流还需要明确目标会话，或明确要求新建会话。

发现结果至少应提供：

- 稳定身份、所属设备、工具类型、实例名称。
- 在线状态、连接健康、忙碌状态和信息更新时间。
- 可访问的项目与资源范围、可提供的能力。
- 支持的操作：新建任务、继续会话、收取普通消息、唤起处理、取消等。
- 当前调用者是否有联系或委派权限。

发现以用户主动接入和授权可见的设备 / 实例为基础。扫描到工具安装不等于登记成功，也不等于能接任务。

消息、会话与任务分别记录身份和关联关系。普通询问不一定创建执行任务；消息是否进入某个会话，以及是否触发执行，需要明确语义。

## 6. 核心交互流程

### 6.1 发现与普通交流

1. Agent A 查询自己有权联系的 Agent。
2. 根据目标能力和环境，选择 Agent B。
3. A 向 B 发送问题或资料，指定会话或说明新建交流。
4. B 的接入端按支持的方式投递请求，并报告投递 / 处理状态。
5. B 返回回复或补充问题，A 在原工作流程中继续交流。

保留普通消息能力，例如询问项目进展、请求已有分析、确认环境信息。方案不只包含新建远端任务。

### 6.2 任务委派与结果回收

1. A 向 B 提交任务目标、输入、环境要求、完成条件与预期交付物。
2. Bridge 返回任务标识，记录发起者、目标及父任务 / 原会话关联。
3. B 执行任务，回传进度；需要信息或授权时进入等待状态。
4. A 或用户处理等待事项，Bridge 将回复路由回原任务。
5. B 返回实际结果、报告或文件；A 根据结果继续工作并向用户汇总。

提交被接收、目标开始处理、任务执行完成应分别表示，不能把投递成功当成执行成功。

### 6.3 使用示例

用户在笔记本的 Agent A 中提出：

> 联系台式机上的 Agent B，确认它是否能访问这个项目的指定版本；如果可以，让它运行测试、分析失败原因，并把报告返回。

A 先查询目标和环境，再委派任务。B 如需文件或版本信息可回问；执行完成后返回报告。A 继续当前会话，整理结论并决定下一步。

此例同时验证发现、双向消息、任务执行与结果回传。

## 7. MCP 操作草案

以下名称仅用于表达能力，不是已经实现或最终确定的接口。

| 操作示意 | 用途 |
| --- | --- |
| list_agents / get_agent | 查询有权访问的 Agent、环境和能力 |
| send_message | 向目标 Agent / 会话发送普通消息或补充信息 |
| get_messages | 按游标读取新消息与回复，支持重复读取去重 |
| submit_task | 委派任务，明确目标实例及新建 / 继续会话方式 |
| get_task | 查询进度、等待事项、错误和终态 |
| reply_task | 回复原任务的补充问题或经授权的控制事项 |
| get_artifact | 读取任务交付物或可访问的文件引用 |
| cancel_task | 请求取消并观察目标是否实际停止 |

返回结果应包含可关联的消息 / 任务标识、当前状态和可用的后续操作。长任务采用异步处理，客户端可以查询或订阅更新；具体接收机制按宿主能力确定。

## 8. 上下文、产物与可靠性

- 请求明确说明目标、相关资料、项目版本、工作环境和完成条件。
- 不假定两台设备共享文件路径。文件需要可访问引用或受控传输，并能核对所属任务与版本。
- 按需要共享上下文；不默认同步整个会话历史、模型凭据或全盘文件。
- 保留消息顺序、回复关联和父子任务关系；记录来源，避免送错实例或会话。
- 提交和控制请求使用稳定请求标识；重复投递不能导致重复执行。
- 离线、超时或失联时展示真实状态。结果不明时查询、恢复观察或核对原执行，不自动重发任务。
- 取消区分“请求已收到”与“执行已确认停止”；已经产生的文件修改不会自动撤销。
- 用户授权限定可见目标、可访问资源和可执行操作；Agent 间请求不能替用户扩大权限。
- 用户能查看参与者、消息与任务状态，并请求停止协作。
- 自动委派设置层级、次数、时长或预算边界，避免循环调用和无界扩散；具体默认值待定。

## 9. 初版建议与后续阶段

### 第一阶段：发现与跨设备委派闭环

建议面向单个用户主动配对的可信设备，先支持两台物理设备、少量明确适配的 Agent 工具。

交付发现、能力查询、向接入端管理的会话发送请求、远端任务创建 / 续问、等待处理及结果回收。普通消息可先由明确支持的会话模式承载；不支持的目标明确返回能力限制。

暂由任务发起 Agent 协调，管理界面提供过程可见性。优先复用现有 Hub / Edge 和任务记录能力，具体部署方式另行评审。

### 第二阶段：已有会话交流与双向通知

扩展适配器支持的已有会话接入、主动查询 / 订阅新消息、异步回问和资料交换。

明确哪些会话是 Bridge 托管、用户显式绑定或原生接口可接入；分别标注可读、可续问、可接收消息与可唤起能力。

### 第三阶段：更灵活的协作组织

根据实际使用需求，再考虑多级委派、接力协调、对等协作、自动选择执行者和团队共享。管理界面可在同一底层能力上增加方案 1 的协作组织体验。

## 10. 第一阶段验收目标

以下是后续验收目标，尚未执行：

1. 两台不同物理设备上的真实 Agent 完成 A → B → A 协作，不以 Mock 或 Windows + WSL 替代。
2. A 能获取准确的目标身份、在线状态、环境与受支持操作。
3. A 能发送问题、收到 B 的回复，并继续一次相关交流。
4. A 能委派明确任务、观察进度、处理一次补充问题并取得真实结果。
5. 原会话与任务关联保留，文件 / 报告能被发起者实际读取。
6. 重复提交、断线与恢复不会重复执行原任务；未确认结果保留可查询状态。
7. 未授权目标或资源被拒绝，Agent 请求不会绕过用户已有操作权限。
8. 用户可从管理界面查看协作过程，并请求取消；显示的终态与原生执行证据一致。

## 11. 待定问题

- 优先适配哪些 Agent 工具，以及各工具能接入哪些已有会话。
- 接收消息采用主动查询、订阅推送、适配器投递还是唤起执行；允许按工具分别实现。
- 普通消息与任务委派如何共享会话上下文，何时创建新的执行轮次。
- Hub 部署在哪台设备，是否需要中继，以及局域网 / 外网的接入顺序。
- 内部协议复用现有协议还是引入 A2A；对外 MCP 与内部通信协议分别评审。
- 哪些协作请求可由 Agent 自动发起，哪些需要用户确认，授权如何撤销。
- 多级协作的默认深度、并发、超时与预算，以及文件传输与保留策略。

后续细化时，应把“产品愿景”“初版必需能力”“适配器实际支持”和“验收证据”分别标清。
