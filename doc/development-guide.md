# 人类与 Agent 共同开发、维护规则

适用所有后续迭代与模块修改。[根 AGENTS.md](../AGENTS.md) 将这些规则提供给开发 Agent。

## 1. 一次变更应交付哪些材料

| 材料 | 写什么 | 必须更新的情况 |
| --- | --- | --- |
| 当次迭代需求/开发记录 | 本次需求、边界、验收目标、实际改动与未完成项 | 每次产品功能变更 |
| `product-design.md` | 整体功能目录、用户流程、功能现状或模块修改记录 | 每次产品功能变更；反映模块对整产品的影响 |
| 模块 `design.md` | 变更后的完整行为、规则、接口与数据 | 每个受影响模块 |
| 模块 `test-report.md` | 实际运行、版本、结果、证据级别、限制 | 每个受影响模块 |
| `architecture.md` / `data-model.md` / `protocol.md` | 分层、归属、数据格式、协议与兼容说明 | 对应合约发生改变；必须检查，未改变可以在迭代说明 |
| `testing.md` / `project-plan.md` | 基线、整体已交付状态与下一工作 | 改变验收基线、发布状态或迭代范围 |
| 原始证据 | 日志/报告/构建清单/摘要/截图等 | 实际执行相应检查后生成 |

正文更新为最终实现，不在模块页无限追加“后来又修了一次”的流水账。变更的前后原因、历史和日期放在迭代文档；模块页保留简短变更来源。

仅修正文案、拼写或链接时，更新受影响文档并跑文档检查即可，不要求模拟一轮产品验收。纯实现重构若没有行为改变，也要在迭代记录中说明，并核对模块代码落点与测试报告；不要为了满足形式而虚构新需求。

## 2. 开始开发前

1. 从 [文档入口](README.md) 找到整体功能编号 `AB-Fxx` 和模块 `Mxx`。
2. 读模块设计、测试报告与当次迭代，识别“已实现”和“已确认设计”的区别。
3. 核对实际源码和版本。设计与源码有差异时登记缺口；不能把有缺陷的实现直接改写为“已达到设计”。
4. 明确变更场景、成功行为、错误行为和验收方式。用户已经授权的范围继续执行，不因这些维护规则增加审批流程。

## 3. 实现与验收顺序

```mermaid
flowchart LR
  Need[需求与验收目标] --> Impact[整体/模块影响]
  Impact --> Code[实现与适当验证]
  Code --> Evidence[保存实际证据]
  Evidence --> Module[更新完整模块设计和报告]
  Module --> Overall[更新整体功能与接口资料]
  Overall --> Iteration[更新当次迭代结果]
  Iteration --> Check[文档检查与交付核对]
```

报告在测试实际执行后填写。遇到账号、模型或环境限制时保留真实失败，写明阻塞条件；不能换新会话冒充续接，不能用 WSL 冒充独立服务器，不能用界面模拟冒充原生回复。

## 4. 编号与追踪

- `AB-F01` 等：整体产品功能，定义在 [整体设计](product-design.md)。
- `M04-F01` 等：模块细化功能，定义在对应模块设计。原生子模块使用 `M06-OC-Fxx`、`M06-CC-Fxx`、`M06-CX-Fxx`。
- `T-M04-01` 等：模块测试报告的验收项，关联功能编号和实际测试文件/用例。
- 原 I01–I06 需求编号继续保留，迭代中写清关联模块；不因整理文档改写历史编号。

一份测试可支持多个功能，但只能在全工程统计一次。没有真正运行的设计用例只能写“未测试”，不能与 passed 混合统计。

## 5. 每份设计的最小内容

模块设计应说明：谁使用、提供哪些功能、当前发布/实现状态、与邻居的边界、身份与数据、正常/失败流程、关键接口、能力限制、代码入口、测试报告与迭代来源。

具体实现放到模块。整体资料说明系统关系与用户行为，避免用一页数百行函数清单替代解释。遇到多进程、多身份、状态恢复或多轮流程，优先画小型 Mermaid 图，再用表格解释各对象/分支。

代码示例必须是实际存在的方法和参数。未来 API 写在“已确认设计/待实现”部分；示例使用占位地址和测试 ID，不复制真实密码、Token、私钥、完整敏感命令行或账号配置。

## 6. 每份测试报告的最小内容

| 字段 | 要求 |
| --- | --- |
| 基线 | 验证日期、源码/包版本、系统/工具版本或“未刷新”说明 |
| 场景与功能 | 用户能理解的场景及模块功能编号 |
| 结果 | 通过、部分验证、未测试、失败/环境限制 |
| 证据级别 | 受控测试、真实生产后端无推理、界面模拟、真实工具、真实发布包 |
| 来源 | 实际测试文件/用例和持久报告/日志链接 |
| 复现 | 对应命令、需要的环境，以及是否会调用模型或部署远端 |
| 限制 | 尚未证明什么，缺哪个环境/数据/原生能力 |

历史真实证据继续标注原日期与版本。本次没有重新连接服务器时，不能把历史记录描述成今天的网络状态。

原始日志放 `artifacts/` 下的有日期目录。敏感开发状态不复制到公开报告；报告引用必要的脱敏事实即可。旧验收文件若被脚本覆盖，先保存当次基线副本。

## 7. 具体同步示例

修改 SSH 安装上传方式时，至少更新：

| 文档 | 本次应反映的事实 |
| --- | --- |
| 当次迭代 | 为什么修改、安装耗时目标、实际链路与未测项 |
| M04 设计 | 归档格式、流水线、执行前校验、失败/重试处理 |
| M04 报告 | 相应受控与真实安装结果；无 Node 分支是否实测 |
| 整体功能设计 AB-F06 | 安装用户体验或当前验收状态；列变更来源 |
| 架构 / 协议 / 数据 | 仅在通信合约、目录布局、包清单发生改变时改对应正文 |
| M10 报告 | 新包是否含最终源码、离线资源是否一致；未构建则写未测试 |

修改协作权限时同步 M08、整体 AB-F12/13、父子任务与来源规则，检查 M03/M07 及界面操作。不只更新节点图文案而遗漏后台授权规则。

## 8. 交付时的检查

在仓库根执行：

```bash
node scripts/check-docs.mjs
```

检查 Markdown 本地链接、必需模块设计/报告及追踪编号。它不证明代码正确或模型执行成功。

再运行与改动相应的工程检查和已约定验收。核对源码版本、候选包、实际包内文件与报告一致；有未测项就明确保留，不能因为剩余时间少而标完成。

## 9. 资料归档

每类读者的当前说明各有明确来源。内部完整设计与追踪材料位于原模块目录；用户说明位于 `doc/user/`，同一行为变更时同步两类正文，不维护重复HTML。`doc/iterations/` 是变更历史和当前开发安排；`doc/archive/` 是整理前资料，不能覆盖当前实现说明；`doc.md` 是原始初稿。旧路径 `docs/` 不新增资料。

模块测试报告与证据保留“核对日期”；主文档与模块设计文档只维护当前状态，不带日期戳。新增模块时同时登记模块目录、功能目录、测试汇总和检查脚本，不依靠某个 Agent 的聊天记忆维持项目知识。

## 网页入口同步

用户文档站仅发布 `doc/user/` 明确登记的页面，内容为最新功能、系统设计和使用说明；不出现内部功能编号、测试报告、问题、开发过程、迭代与历史，也不向用户提供这些材料的下载或搜索入口。内部实现资料继续保留，不通过网页暴露。

用户行为变更须同步公开用户页与相应内部设计。六方式接入表从内部当前矩阵提取，能力表从静态适配器注册表生成；不复制矩阵中的验收、源码和规划段落。新增用户页同时登记清单与导航。

使用 `npm run docs:dev` / `docs:test` / `docs:build` / `docs:preview`，细节见[网页说明](web-reading.md)。构建须通过公开页、链接、搜索与资源边界检查。网页行为改动同步M11和所属迭代，按桌面范围验收。
