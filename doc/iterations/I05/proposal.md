# I05 调整提案：机器上的 Agent 节点与主从协作

日期：2026-10-10。状态：用户已批准 I05A + I05B 开发；0.5.0 实现与验收见 [节点模块](node-design.md)、[协作模块](collaboration-design.md)、[验收报告](acceptance.md)。0.4.7 为调整前基线。

## 1. 产品目标

用户先看到接入的机器，以及每台机器上的 OpenCode、Claude Code、Codex 等 Agent 节点；然后指定一个主 Agent 和它可以连接、管理的子 Agent。向主 Agent 提交需求，由主 Agent 发现子节点、分派工作、读取进度和汇总结果。

Agent 节点是某个执行环境中的工具接入身份，与项目目录、供应商、模型和单次进程无关。Windows 与 WSL 发行版分别作为执行环境显示，并标明同一物理宿主。其他物理电脑接入使用同一对象模型，真正的远程通信继续单独验收，不能以 Windows + WSL 冒充跨电脑交付。

## 2. 当前实现差距

| 方面 | 0.4.7 的实际实现 | 调整后的要求 |
| --- | --- | --- |
| 机器 | 桌面目录管理本机及 WSL，按机器汇总后台记录 | 保留稳定机器身份，机器下直接展示 Agent 节点，空机器也可见 |
| Agent 身份 | `AgentInstance extends Agent`；Agent 要求 workspace，后端提交要求先找到项目实例 | Agent 节点独立注册；没有项目和会话也存在；一个节点服务不同任务目录 |
| 发现 | MachineRouter 按系统硬编码 Windows=Claude、其他=OpenCode；适配器类型只有两种 | 按机器实际安装扫描支持的工具，保留工具类型；同机器可有多种工具，不按系统猜类型；增加 Codex 发现 |
| 设置 | 项目实例提供模型/供应商覆盖，连接后的主要入口是添加实例 | 节点接入不选择项目、模型、供应商；执行继承原生配置，不注入模型覆盖 |
| 主 Agent | `defaultAgent` 只决定人工提交的默认目标 | 主 Agent 是协作关系的协调者，有实际查询和委派子 Agent 的接口 |
| 子 Agent | 用户分别操作实例；已有 allowlist 是用户/Connector 到旧 Agent 的访问约束 | 保存主节点到子节点的定向关系，在后台执行发现、任务和控制范围校验 |

代码核对入口：`desktop/src/types.ts`、`desktop/src/App.tsx`、`desktop/electron/machine-router.cjs`、`src/config.ts`、`src/controller.ts`、`src/hub.ts`。这是产品对象与执行接口调整，不能只改页面名称。

## 3. 对象与界面

| 对象 | 含义与归属 | 不应承担的配置 |
| --- | --- | --- |
| Machine | 已登记的执行环境：名称、系统、连接状态、最近同步、物理宿主关联 | 项目、模型、供应商 |
| AgentNode | 所属机器、工具类型、稳定节点 ID、名称、版本、调用入口、接入状态和适配能力 | 固定项目目录、供应商、模型 |
| Collaboration | 用户指定的主节点及允许连接的子节点，保存关系和修订号 | 代替原生 Agent 作模型推理 |
| Conversation / Task | 来源节点、目标节点、原生会话、输入与结果；需要操作文件时记录执行目录 | 改变节点身份或把其他节点的会话迁移过来 |

身份由稳定机器 ID + 工具接入配置确定；升级版本或换项目不生成新节点。同一机器上的不同工具属于不同节点；同工具不同登录/执行配置只有明确登记为独立入口时才区分，不按打开的终端数自动生成节点。

机器页示例（Codex 是否安装由扫描结果决定，不预置在线记录）：

```text
DESKTOP-JR5J3AA · Windows · 在线
  Claude Code   已接入
  Codex         已发现 / 尚未支持执行（若实际安装且仅完成发现）
WSL · Ubuntu · 在线 · 属于 DESKTOP-JR5J3AA
  OpenCode      已接入
```

机器页展示所有接入机器的已发现受支持工具，以及曾登记但当前离线/缺失的节点。区分“已发现”“已接入”“离线”“工具异常”“尚未支持执行”；发现安装不等于模型能够真实回复。未知工具不能宣称自动发现和可执行。

协作页使用主 Agent 单选、子 Agent 多选和保存按钮。首版先提供一组默认协作关系，数据模型保留扩展多组的空间。主 Agent 由用户指定，不固定 OpenCode，不把默认提交目标自动升级成主 Agent。

```text
主 Agent：Windows / Claude Code（仅示例，用户决定）
  └─ 允许连接：WSL / OpenCode
```

目录在新建会话/委派任务需要文件操作时指定，属于目标机器；纯文本交流可使用节点的托管会话目录。托管目录只是运行上下文，不参与节点发现、身份或可见性。续问沿用原会话目录，不能静默换目录。跨机器不假设目录名称相同、文件自动共享。

节点页面和新建流程移除模型、供应商选择。原生工具返回模型错误时显示原生错误和去对应工具修复的指引，Bridge 不代替用户挑模型或写全局配置。

## 4. 连接关系与主 Agent 能力

连接关系属于 Bridge 中保存的定向授权与路由；数据通过各机器接入端及 Hub 转交，不要求两个 CLI 直接建立网络连接。

1. 人工机器页可以看到所有已接入节点；主 Agent 的发现接口只返回当前关系中允许访问的子节点及其实际状态、能力。
2. 主 Agent 可以查询子节点、向它委派任务、读取自己委派的任务和结果、处理原生支持的等待项、请求取消自己委派的执行。这里的管理指协作工作管理。
3. 新增/删除节点、改变主从关系、安装工具、修改原生账户配置仍由用户操作。主 Agent 的发现不自动把新扫描节点纳入授权。
4. 主 Agent 通过任务作用域的 MCP/CLI 接口获得上述操作能力；只在 UI 画连线或把子节点名单写进 Prompt 不算交付。
5. 子结果回到原主会话：记录父子任务和原生会话关联，由主 Agent 继续处理并总结。投递成功、执行完成、主 Agent 汇总完成分别记录。
6. 同机器不同工具也可形成主从关系。首版不做多级递归委派；禁止自身为子节点，重复关系合并，不能借子节点把授权扩展到第三节点。
7. 撤销关系立即阻止新的委派；已有执行记录保留，继续只读核对，终止仍是明确的取消操作。关系变更不自动换目标或重发未知任务。

## 5. 分两个增量交付

### I05A：机器节点模型与协作关系配置

交付：

- 机器下自动列出节点；Windows/WSL 各扫描 Claude Code、OpenCode、Codex，按实际安装显示，Codex 执行能力如未完成则明确标记。
- 节点可登记接入，不必创建项目实例；Claude/OpenCode 的目录上下文移到具体会话/任务，保留直接提交任务入口。
- 移除节点及新任务的模型/供应商覆盖；执行使用原生配置。
- 主节点单选、子节点多选、关系保存和重启恢复；后台保存真实关系对象。
- 迁移旧实例：同机器同工具接入归并为节点；旧项目保留为会话上下文/历史入口，不生成多个项目 Agent。

验收：

| 条件 | 指标/方法 |
| --- | --- |
| 空配置看到机器和节点 | 没有项目时仍看到 Windows、Ubuntu 及实际发现的受支持工具；扫描/登记新增原生 Prompt = 0 |
| 扫描与身份准确 | 用两个执行环境、多工具安装夹具验证；重复扫描和重启后重复节点 = 0；同名工具来源混淆 = 0 |
| 接入流程简洁 | 节点接入必需项目、模型、供应商字段 = 0；Claude/OpenCode 新建普通会话各真实回复一次，执行未传模型覆盖 |
| 关系持久化 | 保存并重开后主/子选择一致；拒绝自身、重复关系和不存在节点；离线节点保留且说明原因 |
| 历史与迁移 | 原 task/request/conversation/native session ID、回答和来源错配/丢失 = 0；再次迁移不重复；旧模型覆盖保留为历史元数据，不静默带入新执行 |

I05A 验收表示节点和关系配置可用，不能宣称主 Agent 已能自动协作。

### I05B：真实主 Agent 到子 Agent 的协作闭环

交付：

- 接入主 Agent 可调用的发现/委派/进度/结果/取消接口，按调用身份校验关系，不只依靠提示词约束。
- 跑通主会话 → 子任务 → 返回结果 → 主会话继续总结，桌面可以展开整条关系与执行记录。
- Windows Claude 与 WSL OpenCode 都可选为主节点或子节点；Codex 原生执行与协作接入纳入本增量，必须完成专门适配与真实验证才能标记可用。
- 子节点离线、异常、等待用户输入、请求结果未知都有明确状态；单边失败不影响其他节点。

验收：

| 条件 | 指标/方法 |
| --- | --- |
| 自动协作真实闭环 | Claude → OpenCode → Claude、OpenCode → Claude → OpenCode 各 1 条真实链；有接口调用、子原生回复及主会话续接证据，人工转述结果 = 0 |
| 用户真的只需向主 Agent 发需求 | 一条需求触发发现和委派，子结果由主 Agent 读取汇总；主 Agent 未调用工具不能用 UI 手工路由冒充 |
| Codex 能力 | 在安装且完成原生登录的环境验证：发现、原生回复、作为主和子各 1 条协作链；未验证项单独列出，不能写已支持 |
| 关系约束 | 已允许/未允许/撤销/伪造来源均有后台合约测试；越权委派和扩大授权成功次数 = 0 |
| 去重与中断 | 同一委派请求重复提交 10 次原生执行仅 1 次；断线重连和重开不自动补发未知 Prompt |
| 关联与异常 | 父子任务、机器、节点、原生会话错配 = 0；子失败不显示成功；保留其他节点可用性 |

## 6. 开发模块与兼容策略

| 模块 | 改动 |
| --- | --- |
| Core / Storage | 增加节点与协作关系；拆开节点身份和任务执行上下文；保留旧身份映射、原请求和原生 Session |
| MachineRouter / 设备接入端 | 去除按系统猜适配器；聚合节点发现与状态；以来源机器和节点路由；项目资源锁改为按实际任务目录判断 |
| Controller / Driver | 去除节点配置必需 workspace；任务执行上下文创建/复用；继承原生默认设置；新增 Codex 适配 |
| Hub / 协作接口 | 定向关系校验、主节点身份、任务作用域操作、父子关联、结果回收和原会话续接 |
| Desktop / CLI | 机器下节点树、状态、接入与关系选择；任务时目录输入；展开委派记录；移除模型/供应商表单 |

旧会话如果依赖历史显式模型覆盖，不允许静默更改绑定后续问。保留原记录；无法在继承原生设置的规则下续接时说明原因，并提供新会话入口。旧模型配置不作为新节点属性，也不在迁移时修改原生全局配置。

迁移前备份、原子写入、重复迁移检查；任务未知占位和原请求只读核对规则继续保留。开发顺序为身份和迁移 → 多工具发现 → 会话上下文 → 桌面关系 → 协作接口和真实链路。

## 7. 与既有计划和 Multica 的关系

用户本次明确的节点定义取代 I04B 的“项目实例作为 Agent”及旧协作备忘中按执行实例发现的方向。I04B–I04G 仍保留为历史交付记录；本提案确认后作为后续需求基线，不追改历史验收结论。详细需求、开发、测试文档在确认增量后按单点建立。

Multica 的 [Daemon and runtimes](https://multica.ai/docs/daemon-runtimes) 说明：后台在机器上发现工具，一台机器可登记多个工具运行节点。它的 [Squads](https://multica.ai/docs/squads) 说明：用户选择一个 leader 与成员，leader 分派工作。这里参考这两种组织方式；本项目 AgentNode 对应用户要求的工具节点，名称和模型设置规则由本项目要求决定，不复制 Multica 的 Agent 配置对象。
