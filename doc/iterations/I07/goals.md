## 1. 已确认目标与边界

AgentBridge 负责连接外部已具备功能的智能体、组织小队、传递任务与结果，不负责实现、配置或训练智能体的业务能力。目录、Skill、模型和执行方法由外部智能体管理；Bridge 不增加模型 API 层。

同一底层工具可承载多个外部智能体，例如编译智能体与运行智能体。只有外部提供可区分的调用入口或实例身份时，Bridge 才能分别登记；不能仅凭两个名称创建隔离、执行能力或释放原 unknown 占位。工具安装节点继续保持原身份，外部智能体登记使用独立对象，不直接改写现有节点含义。

| 需求 | 目标 | 模块关联 | 完整目标（实际覆盖见验收矩阵） |
| --- | --- | --- | --- |
| I07-R01 | 用户登记外部智能体的名称、连接信息与对外能力介绍 | M03、M06；关联 AB-F02/03/07 | 两个共用底层工具、具有独立入口的外部智能体可分别找到并调用，原工具节点身份不被混用 |
| I07-R02 | 用户组织小队并指定一个主智能体 | M03、M08；关联 AB-F12/13 | 主智能体可查询获准队员的职责、输入/输出说明和实际状态；队员看见谁、可调用谁按明确授权处理 |
| I07-R03 | 通过 Bridge 传递任务、状态与真实结果 | M06、M07、M08；关联 AB-F07/09/11/13 | 外部执行可关联原任务；不确定响应查询原请求，不换 ID 重发；登记介绍不作为能力实测证明 |

连接适配只转换通信，不接管编译、运行等业务流程。对外介绍可以由外部智能体提供或由用户填写，当前记录为用户声明并标注来源，登记、小队及I07A/B接口已实现，用户自研产品尚未实测。旧MCP主从协作继续按原授权运行。

## 2. 当前讨论场景：写代码、编译与返修

用户提出：主智能体安排 A 写代码、B 编译；B 的错误需要到达 A 和主智能体，主智能体持续跟进直至得到可核对的交付结果。

用户进一步提出小队维护公共文档，明确成员能做什么、不能做什么，并参考 Claude Projects。官方资料见 [调研](claude-projects-research.md)；公共文档、群消息、任务板、成员权限、授权交接和主角色持续激活已在 [细化设计](design.md)形成全量语义；其中I07A接入基础与I07B任务板/授权交接已实现，自动激活等待I07C。当前MCP/SQLite及边界见[I07B交付](task-handoff.md)，完整方案覆盖以下问题：

- 队员通过公共空间直接反馈与交接，主智能体可见并协调；共享工作文档、群消息和任务状态如何配合，通知与执行任务分别处理，避免重复返修。
- 主智能体怎样持续接收事件；原回合已结束时怎样恢复协调；保留原任务归属，不扩大现有父执行 scope。
- A 返修、B 复验怎样关联同一总任务、具体轮次和同一份代码版本；跨机器产物如何可达，不能假设共享目录或文件自动同步。
- 任务完成条件、失败/停滞、权限等待、预算与停止边界；不能用“任务已接收”或智能体自称完成替代实际验收证据。
- 主智能体负责判断下一步，Bridge 负责可靠传递、记录与恢复；不把业务智能下沉为 Bridge 内置模型。
