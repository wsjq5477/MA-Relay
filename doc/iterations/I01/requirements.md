# I01 需求规格：CLI 基础任务闭环

版本：1.0  
日期：2026-10-08  
状态：迭代范围与开发已获批准；I01 已实现并通过本地自动验收，待用户复核。  
范围依据：[迭代计划](../../project-plan.md)。本文集中描述八项需求及其验收条件，设计见 [design.md](design.md)，开发结果见 [development.md](development.md)，逐条验收证据见 [testing.md](testing.md)。

## 1. 交付目标与使用场景

用户在一台 Linux/WSL 主机上启动 Hub 和两个独立 Edge，通过 CLI 发现各 Edge 的 Mock Agent、向指定 Agent 提交任务、查看进度和结果，重启后查询已保存的历史。

| 角色 | I01 中的操作 |
| --- | --- |
| 本地操作者 | 初始化配置、启动进程、提交与查询任务、检查故障信息 |
| Hub | 校验身份、登记 Agent、转交任务、保存状态与结果、提供查询 |
| Edge | 主动连接 Hub、注册本机 Agent、调用 Mock Driver、回传真实事件 |
| Mock Agent | 根据可信测试配置模拟成功、失败和延迟；明确标识自身是测试 Agent |

默认验收拓扑为 1 个 Hub、2 个 Edge，各 Edge 注册一个 Agent：mock-a、mock-b。目标始终按唯一 agentId 指定；显示名称和设备名称只用于辨认。

I01 的演示证明真实跨进程连接和任务管理行为，不代表完成真实 OpenCode、两台物理设备或 Windows 原生验收。

## 3. I01-F01：配置与启动

**用户需求：** 作为本地操作者，我希望使用明确的配置和命令启动 Hub、两个 Edge 与客户端，发现启动错误。

**功能规则：**

- init 生成本地演示需要的配置、受保护的临时凭据及运行说明；输出文件位置，凭据不打印到终端。
- Hub、Edge、客户端支持指定配置文件；相对路径的解析规则固定且可查，不因启动终端不同而悄悄指向其他数据目录。
- 已有配置默认不覆盖；缺少字段、格式错误、凭据缺失、端口占用、数据目录不可用都应明确报错。
- Hub/Edge 以前台独立进程运行，启动输出能辨认角色、配置位置、监听/连接地址和设备；CLI 在另一个进程访问 Hub。
- 本地明文开发模式必须显式启用并限回环地址，身份校验照常生效。I01 不提供正式跨主机部署。
- Hub 数据与两个 Edge 的执行记录使用各自的数据目录；示例无需公司账号、真实 Agent 或模型 API Key。

**验收条件：**

- AC-F01-01：给定空演示目录，初始化后能按说明启动 Hub 和两个 Edge，三个服务进程的 PID 不同，CLI 可访问 Hub。
- AC-F01-02：给定已有配置，再次初始化明确拒绝覆盖，原文件内容保持原值。
- AC-F01-03：给定非法配置或不可用启动资源，命令非零退出并指出原因，不宣称服务就绪；输出无身份凭据。

## 4. I01-F02：Agent 注册与查询

**用户需求：** 我希望知道有哪些 Agent、分别在哪个 Edge，以及当前是否能提交新任务。

**功能规则：**

- Edge 主动连接 Hub，仅能注册其身份被允许的 agentId；agentId 全局唯一，设备名不是身份凭据。
- 一个 Edge 可以注册多个已配置 Mock Agent；验收示例使用两个 Edge 各一个 Agent。
- 同一 Connector 身份存在活跃连接时，第二个连接明确拒绝；不同 Connector 冒用相同 agentId 也拒绝。
- agents 至少显示 agentId、名称、Adapter 类型、设备、在线/离线、健康状态、忙碌状态及当前任务摘要。
- 在线、健康和忙碌是独立信息。连接存在不代表 Driver 健康，任务未结束或 unknown 时不能显示可接单。
- Edge 退出、连接关闭或超过配置的心跳检测窗口后显示离线；展示不应无限保留“在线”。
- 重启后重新注册同一合法身份更新原 Agent，不能生成多个难以区分的逻辑 Agent；unknown 的占位不会因此解除。

**验收条件：**

- AC-F02-01：两个合法 Edge 注册后，CLI 能区分 mock-a/mock-b 的所属设备与能力，每个 agentId 只有一个逻辑记录。
- AC-F02-02：重复活跃连接或冒用身份被拒绝，既有 Agent 归属和任务状态不变。
- AC-F02-03：停止一个 Edge，在配置的检测窗口结束后显示离线；另一个 Edge 的在线与任务执行不受影响。
- AC-F02-04：延迟任务运行时显示忙碌及对应 Task ID；unknown 时显示不可接单及原因。

## 5. I01-F03：指定目标提交任务

**用户需求：** 我希望把消息交给明确的 Agent，并在重试提交时不会意外创建第二个任务。

**输入与返回：**

- 输入为 agentId 和消息；消息来源为位置参数、stdin、文件三选一，文件在客户端读取后传递内容。
- 消息须为非空白 UTF-8 文本；保留有效消息的换行与内容。消息大小按 UTF-8 字节计，默认上限 64 KiB，Hub 可以配置更低上限；超限明确拒绝。
- 每次逻辑提交有 requestId。CLI 自动生成并让用户可获取，也支持 --request-id 显式指定；提交响应不明确时必须保留该 ID 供显式重试。
- 创建成功返回 taskId、conversationId、requestId、targetAgent、当前状态；Task ID 表示任务已持久化，不表示已执行完成。
- I01 为新任务生成 Conversation 关联，不提供原生会话续接或父子任务提交。

**业务规则：**

1. 身份、调用权限和输入校验始终生效。
2. 先检查当前身份的 requestId 是否已有提交记录。同 ID 同目标/同消息返回原 Task，不受目标此刻忙碌、离线或原任务已 unknown 的影响。
3. 同身份、同 requestId 使用不同目标或消息，返回冲突；原任务、原载荷和执行次数不变。
4. 只有新提交才检查目标在线、健康和空闲；不存在、离线、不健康、忙碌或被 unknown 占位的目标明确拒绝。
5. 创建成功即占用该 Agent 的执行名额。每个 Agent 最多一个未结束任务；不同 Agent 可以分别执行。
6. 多个不同请求同时争抢同一空闲 Agent，最多一个创建成功；被拒绝的请求不创建任务，也不绑定 requestId。
7. 用户用不同 requestId 再次提交相同消息，属于新的逻辑任务，不能承诺识别用户意图后自动合并。

**验收条件：**

- AC-F03-01：向有权限的在线空闲 mock-a 提交消息，返回可查询 Task ID，只有 mock-a 实际执行；参数/stdin/file 输入一致。
- AC-F03-02：不存在、离线、忙碌、空白/超限消息被拒绝，新增任务及 Driver 调用数均为 0。
- AC-F03-03：同身份、同 requestId、同载荷提交 10 次，包含并发请求，唯一 Task 数和实际执行次数均为 1；目标后来离线时仍能取回原 Task。
- AC-F03-04：同 requestId 改变目标或消息返回冲突；多个不同请求争抢一个 Agent 时最多接受一个。

## 6. I01-F04：Mock 执行与任务状态

**用户需求：** 我希望验证任务确实由目标 Edge 的 Driver 执行，并能区分成功、失败和尚未完成。

**功能规则：**

- Mock 明确标识测试身份。成功、失败和延迟由管理员/测试配置控制，配置变更通过重新启动相应 Edge 生效。
- 正常执行产生 started、进度、output 与 completed；失败至少有可关联的执行/失败证据和结构化错误。事件不能只是 Hub 预先生成的成功记录。
- 成功结果能核对原消息与实际执行 agentId；失败保留错误码和可读说明。Mock 的调用有独立持久计数，可证明执行次数。
- 用户消息只作为输入数据，不决定 executable、Shell、工作目录或高权限操作。
- 只有 Driver 的真实结果能确认终态。任务接受、连接正常或传输确认均不能直接判成功。
- 已确认并保存的 succeeded/failed 不被迟到的冲突事件覆盖；重复终态事件不产生额外逻辑事件。
- 只有确定终止并保存终态后才释放执行名额。断线、观察超时或确认丢失不能作为“已经失败并停止”的证据。

| I01 状态 | 用户看到的含义 |
| --- | --- |
| queued | 已保存，正准备本次投递；不是等待离线 Agent 上线的队列 |
| accepted | Edge 已接单，尚未确认 Driver 开始 |
| running | 已观察到真实执行开始 |
| succeeded | 执行完成且结果已确认保存 |
| failed | 有确定的失败证据；包含可区分的执行前失败或 Driver 执行失败 |
| unknown | 执行结果或是否仍在运行无法确认，按 F08 处理 |

**验收条件：**

- AC-F04-01：两个 Edge 各执行 10 个成功任务，20/20 的目标、结果及终态与 Mock 实际调用一致。
- AC-F04-02：两个 Edge 各执行 5 个失败任务，10/10 为 failed 且错误可查询，没有错误成功结果。
- AC-F04-03：延迟场景完成前能观察 running 和进度，不能提前返回终态；业务输入中的特殊字符原样作为数据处理。
- AC-F04-04：重复/非法状态事件不会重复执行、新增重复终态或覆盖已确认结果。

## 7. I01-F05：CLI 查询与观察

**用户需求：** 我希望仅通过 CLI 查看任务的当前状态、历史结果和故障原因，也能用于脚本验收。

**功能规则：**

- 提供 agents、run、tasks、task；启动相关命令见 F01。run 默认返回提交记录，后续用查询/观察查看执行情况。
- tasks 至少显示 Task ID、目标 Agent、状态、创建时间/执行时长、最近摘要；task 显示消息、Conversation ID、状态、事件摘要、结果/错误或 unknown 原因。
- 列表能访问全部授权历史；如有数量限制，明确提示并提供继续查询方式，不能静默遗漏。
- 列表注明仅包含 AgentBridge 创建的任务；I01 不声称枚举所有原生 Agent 活动。
- --watch 持续查看列表或单任务变化。单任务观察在 succeeded/failed/unknown 时结束；unknown 说明需要处理，不显示成成功或确定失败。
- 普通 --json 输出一个 JSON 结果；--watch 与 --json 组合输出逐行 JSON。诊断写 stderr，不混入机器结果。
- Ctrl+C、观察超时、查询失败和重新观察都不取消任务、不重新提交、不改变状态或释放占位。
- 同时区分命令执行结果与 Task 执行结果：查询 failed Task 仍是成功查询。

| CLI 退出语义 | I01 约定 |
| --- | --- |
| 0 | 提交/查询成功；单任务观察获得 succeeded |
| 1 | 单任务观察获得已确认 failed |
| 2 | 参数、配置或权限错误 |
| 3 | 单任务观察获得 unknown，或本地等待超时 |
| 4 | 提交被业务规则拒绝，如目标离线/忙碌/不健康或 requestId 冲突 |
| 5 | 网络/服务不可用，或查询对象不存在/不可见 |

具体参数和输出字段在 CLI 设计时落定，保持上述行为与退出语义。

**验收条件：**

- AC-F05-01：仅使用 CLI 完成发现→提交→观察→结果查询，成功、失败和 unknown 清晰可辨。
- AC-F05-02：文本列表含必要字段；JSON/JSONL 可解析且无诊断混入，授权历史可查全。
- AC-F05-03：观察中断或超时后再次查询，同任务仍按其真实执行状态运行/结束，调用次数没有增加。
- AC-F05-04：提交、查询、观察及错误路径遵循约定退出语义；普通查询 failed Task 返回 0。

## 8. I01-F06：持久化与执行去重

**用户需求：** 我希望重启不会丢失已经确认的任务记录，也不会因为恢复记录而再次执行任务。

**功能规则：**

- Hub 使用 SQLite 保存 Task、Conversation 关联、事件、结果/错误、幂等提交及必要占位信息。
- Edge 在调用 Driver 前保存稳定 taskId/executionId 与执行边界记录；同一执行再次收到不能启动第二次调用。
- 接单和执行事件先保存必要记录再发送；无法保存时不能宣称可靠接单或结果已保存。
- Hub 和 Edge 重启使用原数据目录；终态和幂等关联保持一致，不依靠内存缓存证明去重。
- I01 无自动执行恢复：旧记录用于展示和防重复，不是自动继续或重新投递的指令。
- 详细长输出可限量并明确标记截断；Task 的终态、结果/错误摘要和必要执行证据不能因输出太长而消失。固定基准数据应完整保留。

**验收条件：**

- AC-F06-01：F04 的同一批 20 个成功、10 个失败任务，在 Hub 正常重启后，30 个 Task 的 ID、目标、终态、结果/错误及基准事件丢失数为 0。
- AC-F06-02：重启后用同身份、同 requestId 重放既有提交，返回原 Task，Driver 调用计数不增加。
- AC-F06-03：同执行重复投递或 Edge 重启后出现旧记录，实际调用次数不增加；幂等与故障任务单独计数。
- AC-F06-04：存储故障明确报错，不返回虚假确认；输出达到限制时提示截断且不制造虚假终态。

## 9. I01-F07：身份与访问边界

**用户需求：** 我希望只有受信任的客户端和 Edge 能调用或回写任务，私有记录及凭据受到保护。

**功能规则：**

- HTTP 业务操作及 Edge 连接默认验证凭据，身份由服务端可信配置确定；本地开发模式不关闭身份验证。
- 用户调用/发现 Agent 遵循 allowlist；Connector 只能注册自己的 Agent、回写自己被分配的 execution。
- 用户默认仅查询自己的 Task/结果；详细诊断需对应权限。其他用户的 requestId 或 Task ID 不构成访问授权。
- 任务来源与所有者依据已认证身份生成，客户端自报 sourceUser/sourceAgent 不提升权限。
- 无权限请求不创建 Task、不调用 Driver、不修改事件/状态；输出不得泄漏其他用户的任务内容。
- 日志、错误、CLI 输出和可共享验收材料不显示配置中的身份凭据或敏感环境变量；完整私有诊断默认不共享。
- I01 采用管理员配置的静态身份，不包含账号注册、团队管理或企业登录。

**验收条件：**

- AC-F07-01：缺失/错误凭据、allowlist 外目标、冒用注册或越权回写均被拒绝，无授权业务写入与执行数为 0。
- AC-F07-02：另一静态用户不能凭 Task ID/requestId 查询原用户私有任务与诊断；伪造来源不改变所有者。
- AC-F07-03：正常、失败及非法请求的日志、错误输出和验收材料中，配置凭据明文命中数为 0。

## 10. I01-F08：中断与 unknown 保护

**用户需求：** 我希望执行情况不明时系统诚实显示原因，并避免自动重复有副作用的任务。

**功能规则：**

- 对曾尝试投递、已接单或运行中的任务，断线/进程退出后无法确认结果时，Hub 保存 unknown、原因及最后确认状态。
- Hub 重启先识别未确认终态的历史任务；Edge 重启不重新调用这些任务。已确认保存的 succeeded/failed 始终保留。
- 明确证明未尝试投递的任务，允许记录执行前失败；不能把“没有收到 ACK/结果”作为未执行证明。
- unknown 保留该 Agent 的占位，即使 Edge 重新注册且报告健康，也不能接收新的执行请求。其他未受影响 Agent 仍可使用。
- 用户可以查询 unknown 及已有证据；单任务观察结束并提示本轮无法自动查证。
- I01 不自动重连、重投、迁移到其他 Agent 或恢复执行；用户重启进程不代表授权重跑。
- 执行查证、状态对账、确认执行已结束及安全释放 unknown 占位在 I02 细化。I01 不提供未经定义的重置或改成功操作。

**验收条件：**

- AC-F08-01：实际调用已经开始但终态尚未确认时，分别终止 Hub/Edge 并用原数据重启，受影响任务可从 CLI 与持久记录看到 unknown 及原因。
- AC-F08-02：上述故障前后，同 taskId 的已发生调用次数不增加；自动重跑数为 0。
- AC-F08-03：重新注册受影响 Agent，不解除 unknown 占位；新请求被明确拒绝，同 requestId 的查询式重放仍取回原 Task。
- AC-F08-04：已保存终态不被故障扫描改成 unknown；独立、未受影响的 Agent 可继续提交。

## 11. 范围与非功能约束

- 本轮必须用 CLI 验收；真实 OpenCode 在 I03，看板在 I04。
- 取消、waiting_input/reply、自动重连、离线队列、完整重传/对账与执行恢复属于 I02。
- JSONL/HTTP Driver、Harmes/自研专用接入、委派属于 I05；Webhook、正式部署与 Windows/跨设备最终验收属于 I06。
- 不引入 LLM、模型账号、远程 Shell 平台、资源调度或工作流引擎；Hub 不执行 Agent Driver。
- 保持 TypeScript/Node/npm 单仓库与单 CLI；延迟、吞吐只记录观测值，I01 不承诺性能 SLA。
- 输入和输出有明确可配置限制；超限、截断及存储不可用均可识别，不能无限缓存或伪装为业务成功。
